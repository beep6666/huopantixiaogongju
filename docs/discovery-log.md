# 实现发现日志

以下发现来自阅读现有两个 HTML、把演示数据改成可导入数据、设计稳定 ID 关联、实现规则校验和跑自动测试的过程。它们不是被 Mock 掩盖的问题。

## 发现 1：原轻量版没有真实数据导入

**问题：** 商品、渠道、资源位、项目、规则和结果只能随代码改变，真实人员无法带入一次经营任务。

**为什么实现时发现这个问题：** 原页面全部从 `demoData()` 常量加载，只有逐行 CRUD，没有 CSV/JSON 导入、来源或快照时间。

**它暴露了哪个产品 / 数据 / 业务假设：** 假设 Demo 数据结构足以代表真实数据，且页面可操作等于资料准备价值已被验证。

**影响：** 只能验证演示流程，不能验证“减少搜集、拼接和确认成本”。

**建议验证方式：** 让五类数据 Owner 按模板提供一次脱敏真实快照，完整导入并记录准备时间。

**是否阻塞 MVP：** 是。当前版本已补导入能力；真实文件尚未验证。

## 发现 2：原页面用商品名称做跨表关联

**问题：** 改名、重名、套餐别名会使渠道状态、项目、资源位和结果静默挂错商品。

**为什么实现时发现这个问题：** 原页面的 `channelProducts.product`、`projects.product`、`slots.current` 都保存展示名称，且共创看板明确提到“改名等于换码、统计断了”。

**它暴露了哪个产品 / 数据 / 业务假设：** 假设名称唯一、稳定且跨系统一致。

**影响：** 错配风险高于显式报错；整齐矩阵可能制造错误信心。

**建议验证方式：** 抽取 30–50 个真实 SKU 和三个渠道 ID，统计精确、一对多、未匹配；所有歧义由人确认。

**是否阻塞 MVP：** 是。当前版本强制按 `product_id` 关联并阻断未知引用，但还没有身份映射 UI。

## 发现 3：原页面的规则与冲突是硬编码文案

**问题：** 用户修改停售、库存、区域、规则启用状态或项目后，策略页的冲突不会重新计算。

**为什么实现时发现这个问题：** 原页面的 `hits`、`conflicts` 和商品 `filter/filterNote` 是独立常量，没有读取规则表和任务范围。

**它暴露了哪个产品 / 数据 / 业务假设：** 假设示例规则完整、永远有效，且展示冲突等于系统真的检查过。

**影响：** 容易产生虚假的安全感，无法解释漏检或规则来源。

**建议验证方式：** 收集一次真实任务用到的全部规则，尝试放入 7 类模板，统计覆盖率和人工确认量。

**是否阻塞 MVP：** 是。当前版本已改为可追溯的固定模板；不支持的规则仍需人工记录。

## 发现 4：原结果页是硬编码数字

**问题：** 无需执行或上传结果，就会显示整体 +8%、动作商品 +21% 等数字。

**为什么实现时发现这个问题：** 原页面 `renderEffect()` 直接输出固定 HTML，与 task、action、时间窗和数据都无关。

**它暴露了哪个产品 / 数据 / 业务假设：** 假设示例变化可代表闭环已经成立。

**影响：** 可能被误读为真实收益或因果证明。

**建议验证方式：** 使用相同 task、商品和前后窗口口径录入真实观测；回收前保持空白。

**是否阻塞 MVP：** 否，不阻塞资料准备实验；但阻塞“经营闭环已验证”的主张。当前版本已改为人工录入和非因果提示。

## 发现 5：缺数据与业务上不存在容易混为一谈

**问题：** 没上传项目/规则可能被理解成“没有项目/没有冲突”。

**为什么实现时发现这个问题：** 原页面没有数据集装载状态；Demo 数组总是存在。

**它暴露了哪个产品 / 数据 / 业务假设：** 假设页面没显示即代表现实中没有。

**影响：** 对负责人造成错误安全感。

**建议验证方式：** 每类数据区分未加载、已加载 0 行、已加载 N 行、过期、无效；0 行必须由 Owner 确认。

**是否阻塞 MVP：** 是。当前版本区分未加载与 0 行，但还没有独立的 `confirmed_empty_by` 字段。

## 发现 6：销量、库存、渠道和资源位可能不是同一时点

**问题：** 即使五张表都能关联，资料包也可能把昨天库存、上周渠道状态和今天销量拼在一起。

**为什么实现时发现这个问题：** 原数据对象没有 `snapshot_at`；实现真实导入时无法判断新鲜度。

**它暴露了哪个产品 / 数据 / 业务假设：** 假设所有数据天然同步且足够新。

**影响：** 决策上下文内部自相矛盾，扩量动作可能基于过期库存或锁定状态。

**建议验证方式：** 五类快照都提供时间；记录真实延迟，让负责人定义每类可接受 SLA。

**是否阻塞 MVP：** 是，至少必须暴露。当前默认核心快照 48 小时、项目/规则 7 天，仅作为待验证阈值。

## 发现 7：销量与库存口径没有被证明

**问题：** “销量”可能是支付件数、核销件数或净退款件数；“库存”可能是全国仓、区域仓、门店总和或可售库存。

**为什么实现时发现这个问题：** 原页面只有 `sales7` 和“充足/偏紧”，没有指标定义、范围、单位和来源。

**它暴露了哪个产品 / 数据 / 业务假设：** 假设一个销量数和一个库存标签足以跨渠道、跨时间判断。

**影响：** 趋势、低库存规则和前后结果可能失真。

**建议验证方式：** 首单由数据 Owner 为每个数值列写一句口径；抽 10 个 SKU 与补货负责人核对库存可行动性。

**是否阻塞 MVP：** 视真实源而定。当前代码只能校验格式，不能证明业务口径。

## 发现 8：资源位“可调”不是稳定布尔值

**问题：** 可调性可能依赖日期、项目、合同、素材、审批和负责人确认。

**为什么实现时发现这个问题：** 原页面只有 `adjust: true/false`；共创看板又显示变更周知和临时承诺大量存在。

**它暴露了哪个产品 / 数据 / 业务假设：** 假设有一个实时、统一的资源位状态源。

**影响：** 系统显示可操作，实际却不能在 7 天内调整。

**建议验证方式：** 本次所有资源位由 Owner 确认状态、原因、最早可调时间；回看最近 10 个动作的真实上线周期。

**是否阻塞 MVP：** 否。首轮用任务级快照可继续；阻塞建设完整资源位中心。

## 发现 9：任务范围“华东 120 店”无法跨源复现

**问题：** 各来源对“华东”可能使用不同门店集合，只有数量无法重建母集。

**为什么实现时发现这个问题：** 任务表单只有区域文本和门店数，五类输入也没有 `scope_ref` 或门店清单版本。

**它暴露了哪个产品 / 数据 / 业务假设：** 假设区域口径跨系统天然一致。

**影响：** 商品表现、渠道状态和整体结果可能不在同一范围。

**建议验证方式：** 首单冻结 `store_scope.csv` 或至少一个门店集合版本号，对比各源覆盖门店数。

**是否阻塞 MVP：** 若真实源存在区域差异则是。当前页面会提示，但未实现门店清单导入。

## 发现 10：项目与规则可能同时产生相反约束

**问题：** 同一商品可能同时是新品保护和清货对象，单一优先级无法自动裁决。

**为什么实现时发现这个问题：** 任务同时支持“保护新品”和“存在清货任务”，而原页面预设过滤状态试图提前决定候选。

**它暴露了哪个产品 / 数据 / 业务假设：** 假设规则冲突可以由系统自动排序并得出推荐。

**影响：** 自动推荐会越过真正的经营权衡。

**建议验证方式：** 系统并列显示所有命中，让负责人记录选择与依据；复盘实际取舍是否有重复模式。

**是否阻塞 MVP：** 否。这正是必须保留的人工作业点。

## 发现 11：Owner 和 Deadline 不能从策略事实自动推断

**问题：** 一条策略可能涉及渠道、区域、商品和素材多个角色，系统没有组织职责数据。

**为什么实现时发现这个问题：** 原页面把所有 Owner 写成“待指派”，Deadline 固定为已过期日期，页面不能编辑。

**它暴露了哪个产品 / 数据 / 业务假设：** 假设“一键生成执行清单”自然包含正确责任人和时间。

**影响：** 自动填错比留空更危险，清单不能真正交付。

**建议验证方式：** 系统只生成任务骨架，人补齐责任信息；记录补齐时间和是否需要一条策略拆成多任务。

**是否阻塞 MVP：** 否。当前版本已支持编辑与导出，尚未验证 1:1 拆解是否足够。

## 发现 12：前后变化不等于动作效果

**问题：** 天气、节假日、同期活动、门店变化都可能影响销量。

**为什么实现时发现这个问题：** 需求要求基础前后对比，但没有对照组、随机化或因果识别设计。

**它暴露了哪个产品 / 数据 / 业务假设：** 假设 before/after 差值可以归因于策略。

**影响：** 可能错误放大或停止策略。

**建议验证方式：** 本轮固定写“描述性对比”；未来若要回答增量，另立受控实验。

**是否阻塞 MVP：** 否。当前版本不会输出因果字段。

## 发现 13：原页面本身存在流程状态与 DOM 缺陷

**问题：** `strategyHead` 重复 ID；新任务 stage 使用 `plan`，但流程枚举没有该状态；完成态颜色判断了不存在的 `effect`。

**为什么实现时发现这个问题：** 对单文件原型做静态检查和完整函数阅读时发现。

**它暴露了哪个产品 / 数据 / 业务假设：** 假设现有原型已能稳定跑完新建任务路径。

**影响：** 基于它直接叠加真实导入会让状态问题更难定位。

**建议验证方式：** 新实现用明确六步状态和自动测试，浏览器从空白状态完整走查。

**是否阻塞 MVP：** 是。当前版本已绕开原状态模型，未修改用户原文件。

## 发现 14：当前工作目录并不是有效 Git 仓库

**问题：** 根目录有空 `.git` 文件夹，但 `git status` 报“not a git repository”。

**为什么实现时发现这个问题：** 开始检查仓库状态时发现 `.git` 没有任何内容。

**它暴露了哪个产品 / 数据 / 业务假设：** 假设已有版本管理可以保护改动和支持差异审查。

**影响：** 无法用 git diff/commit 回退；多人迭代和实验版本留痕风险较高。

**建议验证方式：** 在团队确认目录边界后初始化正式仓库或迁入现有仓库；本轮通过不覆盖原文件、工作区 JSON 导出和自动测试降低风险。

**是否阻塞 MVP：** 否，但阻塞可靠协作与发布流程。

## 重大调整记录

| 原假设 | 发现的问题 | 为什么调整 | 当前新方案 |
|---|---|---|---|
| 直接在原单文件上继续补功能 | 名称关联、硬编码规则/结果、状态 bug 相互耦合 | 修补会保留最危险的数据假设 | 保留交互思路，重建可测试的 core + UI 两层；不修改用户原文件 |
| 需要完整资源位中心 | 可调性与锁定来源尚未证明，治理成本高 | 不是验证资料准备价值的必要前置 | 首轮上传任务级 `resource_slots.csv` 快照 |
| 项目中心 + 通用规则引擎 | 大量规则仍口头化，模板覆盖率未知 | 过早建引擎会掩盖规则不可获得 | 项目快照 + 7 类固定规则模板 + 未知提示 |
| 商品名称足以关联 | 共创证据和代码都显示改名/别名风险 | 错配会污染全部结果 | 强制 canonical `product_id`，无 ID 则阻断并转身份映射实验 |
| 系统列“推荐商品” | 目标权衡仍属人，数据未验证 | 透明排序也可能偷渡推荐 | 只展示关注信号、冲突与空间，人填写 StrategyAction |
| 前后结果代表动作收益 | 缺少对照和因果设计 | 会产生错误经营结论 | 只计算描述性变化，并持续显示非因果声明 |
| 所有数据有统一实时性 | 各类数据变化频率不同 | 单一更新时间制造同步假象 | 每行 `snapshot_at`，每类显示不同默认时效并待实验校准 |
