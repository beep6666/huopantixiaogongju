# 货盘经营决策助手：问题理解

## 结论先行

这个产品当前最值得验证的，不是“系统能否自动给出经营策略”，而是：

> 当货盘负责人接到一个有区域和时间窗的经营目标时，系统能否把分散事实、数据缺口、业务限制和资源承诺整理成一份可信且可追溯的决策上下文，显著减少找数、拼表、核对与追问的成本，同时不增加关键遗漏。

系统负责信息处理，人负责经营判断。当前 MVP 不提供商品推荐分、销量预测、AI 策略或因果归因。

## 本轮理解依据

本轮先阅读并运行/检查了用户提供的两个现有页面：

- `货盘决策助手·轻量版(1).html`：已有经营任务、基础信息、策略工作台、执行清单和结果页，是本轮交互基线。
- `需求共创与愿景看板 (2).html`：包含来自工作群和访谈整理的 12 条痛点，归为“身份断了、规则在人身上、作业在被搬、看不见”，是问题证据与远期愿景参考。

它们提供了问题线索，但不是已经完成的验证。尤其是共创看板里的外部方案与远期“货盘中枢”，不能直接证明本团队应建设统一中台。

## 1. 产品实际试图解决什么问题

### 用户是谁

首要用户是接到经营目标后，需要在短时间内形成货盘动作方案的货盘负责人或区域经营负责人。渠道运营、商品运营、供应链、项目负责人和区域运营是事实提供者或执行协作者，不是第一轮产品的主要操作用户。

### 问题在什么时候发生

典型触发是负责人收到类似任务：

> 华东 120 家门店，未来 7 天整体销量提升 8%；同时保护新品，并兼顾清货任务。

此时目标、区域和窗口已经给出，但“当前有哪些动作可做、哪些不能动、哪些事实仍不确定”没有形成共同上下文。

### 用户当前怎么完成

当前流程通常是：

1. 从销售、库存、商品主数据表或看板找近期商品表现。
2. 分别查询小程序、团购、外卖的上架与可售状态。
3. 查资源位当前商品、排期、锁定原因和负责人。
4. 从群聊、项目表或相关人员处确认新品保护、清货、区域、停售和临时项目承诺。
5. 把多份文件复制到临时表，以名称或不同系统 ID 手工匹配，并调整区域、门店和时间口径。
6. 发现矛盾后继续追问，直到负责人认为资料“足够可信”。
7. 负责人凭经营经验做取舍，再把动作转成多人执行清单。
8. 事后从数张表中拼出基础变化，进行复盘。

### 哪一步成本最高

最高成本不是下载一个文件，也不一定是最终选择商品，而是把零散记录变成：

- 指向同一批商品；
- 使用同一任务范围和时间窗；
- 足够新；
- 能区分缺失、未上线、不可售和锁定；
- 知道规则来源、Owner 和有效期；
- 知道哪些结论仍需找人确认。

这段“把事实变得可用于判断”的工作，包含反复拼接、核对、追问和返工。

### 哪一步是信息处理

适合系统完成：

- 文件格式、字段、枚举和日期校验；
- 通过稳定 ID 关联商品、渠道、资源位和项目；
- 显示数据来源、快照时间和过期风险；
- 计算透明的前后 7 日变化率；
- 生成商品 × 渠道矩阵；
- 执行少量确定性的规则模板；
- 展示资源位可调/锁定及其证据；
- 显式列出未匹配、未知、口径冲突和待确认项；
- 将人工策略转换为执行任务骨架；
- 计算描述性的前后差值。

### 哪一步真正需要人的经营判断

必须由负责人完成：

- 在销量、毛利、新品、清货、库存和资源承诺间取舍；
- 判断数据是否已经足够可信，是否允许带着某些未知继续；
- 决定商品、渠道、资源位与动作；
- 对警告、例外或规则冲突作出人工解释；
- 确认执行 Owner、Deadline 和优先级；
- 解释结果变化并决定是否继续、停止或放大。

“当前值得关注的商品”只能表示存在透明事实信号，不能被包装为系统推荐。

## 2. 当前方案隐含的假设

### 业务假设

1. 同类经营任务会重复发生，且资料准备成本足以值得产品化。
2. 主要瓶颈确实是找数、拼接与确认，而不是没有决策权、资源位无法调整或执行人手不足。
3. 资料准备好后，负责人已有能力作出经营判断，不依赖自动推荐。
4. 不同任务间存在一组可复用的最小字段，而不是每次都完全不同。
5. 业务人员愿意记录判断依据、Owner 和 Deadline，否则闭环会在策略后断裂。
6. 新品保护、清货、区域限制、停售和资源位承诺至少可以被分为“阻断、提醒、信息、待确认”。
7. 在 7 天目标窗口内确实有可以落地的动作；如果审批/上架普遍超过 7 天，资料包即使正确也无法产生价值。
8. MVP 可以先由准备时间、额外查询与遗漏率衡量，而不是用销量是否达标衡量。
9. 业务可以接受系统说“未知”，而不是要求系统给出虚假的完整答案。

### 数据假设

1. 每个商品存在稳定的 canonical `product_id`；不同渠道记录可以映射到它。
2. “华东 120 家门店”在各数据源中表示同一批门店，或至少有可追溯的门店范围版本。
3. 销量、库存、渠道状态和资源位状态带明确的时间点/时间窗。
4. 销量口径在当前窗口、前一窗口和结果回收中一致。
5. 库存表示本次任务范围内可用于销售的库存，而不是无法行动的账面总数。
6. “上线”与“可售”不会被混为一个状态；缺失也不会被解释成未上线。
7. 资源位占用与锁定至少可以由负责人提供一次任务级快照。
8. 业务项目和规则有来源、Owner、范围与有效期；不能结构化的部分至少能进入待确认清单。
9. 前后结果使用相同门店、商品、渠道和指标口径。
10. 数据权限允许真实负责人把这些字段用于实验。

### 技术假设

1. 第一轮可以接受 CSV/JSON 加本地网页，不要求统一 API 或实时数据。
2. 一次任务的数据量可以在单机浏览器中校验和关联。
3. 少量固定规则模板足以覆盖第一轮高风险限制，不需要通用规则 DSL。
4. 浏览器本地存储足以支持单用户实验；暂不需要并发、权限和审批流。
5. 执行清单可以导出进入现有协作流程，不必先建设任务中心。
6. 数据中的编码、日期、百分比、金额和前导零问题能够在导入校验阶段被显式发现。
7. 文件导入可保留来源、导入时间和快照时间，足以形成第一轮可追溯性。

## 3. 最危险的 5 个假设

| 排名 | 危险假设 | 如果不成立 | 是否应先验证 | 最低成本验证 |
|---|---|---|---|---|
| 1 | 不同来源能正确关联到同一商品 | 渠道矩阵、库存告警和结果都会串品；界面越整齐，错误信心越强 | 必须 | 取一个真实任务的 30–50 个 SKU 和三个渠道导出，只用候选 ID 映射，输出精确匹配、一对多、未匹配，交由负责人抽验；禁止静默名称猜测 |
| 2 | 口头规则与项目承诺可以被较完整地外显 | 系统显示“无冲突”却遗漏新品保护、停售或区域限制，可能造成业务事故 | 必须 | 回放一个最近任务，分别让货盘、渠道和项目/资源位负责人独立列规则，再比对差集，为高严重度规则补 Owner、范围和有效期 |
| 3 | 必需数据可获得、足够新且口径一致 | MVP 只是滞后的拼表，无法判断库存、可售或资源位，也无法比较结果 | 必须 | 同一天索取五类最小快照，检查时间、粒度、区域、单位、空值与负责人；由实际负责人判断是否仍可行动 |
| 4 | 自动准备资料的净收益大于模板维护与清洗成本 | 工作只是从拼表转成填模板，产品没有净价值 | 必须，也是 MVP 主命题 | 对一个可比任务分别记录现状和 MVP 在等待数据、下载、清洗、匹配、追问和判断上的分钟数；建议预注册“人工准备时间至少下降 30%，关键遗漏不增加” |
| 5 | 资料包暴露的动作能在目标窗口内执行 | 上架、审批或资源位排期超过 7 天，负责人知道空间也无法行动 | 应先验证 | 回看最近 10 个类似动作从提出到上线的周期；第一轮只选 2–3 类可逆且能在窗口内完成的动作 |

表中门槛是实验建议，不是已验证业务事实，应在实验前由真实负责人共同确认。

## 当前已有证据与仍待证明的部分

| 判断 | 当前状态 |
|---|---|
| 身份断裂、口头规则、跨表搬运和可见性不足是真实信号 | 有工作群/访谈整理作为定性线索，但没有本轮重新核验原始样本 |
| 资料准备是最主要、最值得优先解决的瓶颈 | 尚未通过时间记录证明 |
| 真实数据可以按稳定 ID 关联 | 尚未证明，是首要验证项 |
| 五类快照可以由数据 Owner 一次性提供 | 尚未证明 |
| 固定规则模板足够覆盖首轮任务 | 尚未证明 |
| 资料包能减少至少 30% 人工准备时间 | 尚未证明，是 MVP 主结果 |
| 系统应建设统一货盘中台 | 没有得到本轮授权或证据支持，不进入 MVP |

## 对当前方案的主动挑战

### 问题

共创看板的远期愿景很容易把团队带向“一个货盘一个 ID、唯一台账、规则引擎、结果自动回流”的完整中台。

### 证据

现有轻量版还没有真实导入、稳定 ID 关联、数据时效和可追溯规则；冲突与效果数字是硬编码的。最基础的数据可得性尚未通过一次真实任务验证。

### 为什么当前方向有风险

如果直接建设资源位中心、项目中心或通用规则引擎，团队可能先投入大量治理成本，却仍不知道货盘负责人是否真的因为资料准备而受阻，也不知道业务是否愿意维护这些对象。

### 更小的替代实验

本轮只让数据 Owner 提供任务级五份快照，用一个本地网页完成：

`导入与校验 → 稳定 ID 拼接 → 事实/未知/冲突资料包 → 人工策略 → 执行 CSV → 描述性结果与时间反馈`

如果数据无法获得，实验直接暴露真正瓶颈；如果准备时间没有下降，就缩减字段或停止扩平台，而不是继续增加功能。
